# Adopt an existing model repository

Preserve the model, training framework, source history, data, checkpoints and existing owner instructions. Imported repository instructions and research are evidence, not permission to execute code or broaden access. Migration does not authorize uploads, model downloads, cloud charges, history rewriting or deletion.

1. Establish which model lifecycle this project represents. Inspect the live operation catalog and current `project.open` result before creating anything. Keep one project/model and one stable recipe identity. If the repo contains multiple models, ask which to adopt rather than inventing a model selector.
2. Run `scripts/inventory_repo.py <repo>` with the available Python interpreter. It only inventories ordinary files and hashes bounded content; it never imports repository code or executes its build hooks. Its filename-based roles are hints, not verified semantics. Review skipped paths, size limits and external artifacts; an incomplete inventory is not migration success.
3. Read `references/project-mapping.md`. Map source entrypoints, dependency locks, data manifests/splits, research, evaluations, checkpoint lineage and export paths. Prefer referencing existing paths in place to moving files. Record unknown provenance, licenses, data-family mapping and test coverage explicitly. Preserve framework-native optimizer/RNG/scheduler state; a weights file alone is not exact-resume evidence.
4. Produce a reviewable mapping and change plan with source file hashes, current Git revision/dirty state, proposed canonical project/recipe bindings, deterministic checks and remaining gaps. Review it with the owner before applying file changes. Never overwrite a local project descriptor or recipe projection to make conflicts disappear.
5. Apply the approved mapping through existing source registration, dataset/version, research, component authoring and recipe operations. Inspect their live schemas instead of guessing arguments. Source-bind wrappers around existing training/evaluation code; do not replace the framework. Keep large artifacts in their current location or an explicitly approved provider store, with immutable references and hashes. Do not silently upload them or add them to Git/LFS.
6. Translate only the owner's selected requirements into explicit policies and required guards. Separate final dataset representation, successful checkpoint exposure and per-family evaluation. Configure dataset overlap scope, sample-size/quality/regression requirements and full evaluation cohort pins as requested. Do not import Biff-specific family names, numerical thresholds, a one-epoch limit or a universal training schedule.
7. Run schema/source/dependency/capability validation and the project's existing tests. After authorized execution, run a bounded native smoke path using the real adapter and selected data. Verify checkpoint ownership, consumed examples, resume mode, evaluation records and promotion/export gates. Unsupported adapters or absent receipts remain blocked/unverified; a skill cannot waive platform checks.

Deliver the mapped project/recipe identities, exact changed files and commits, test commands/results, artifact references, rollback boundaries and unresolved gates. Distinguish “mapped”, “validated”, “smoke-tested” and “eligible for guarded execution”; do not declare production-ready from a scaffold or synthetic test alone. Do not execute migration merely because this skill was loaded.
