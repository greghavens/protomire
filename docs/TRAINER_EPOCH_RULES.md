# Transformers Trainer epoch policy (v2)

Select registered component `modelbuilder.transformers.train`, version `2`, and pin the ordinary wrapper in `examples/transformers_training/epochs_adapter.py`. Version 1 retains its existing weight-only warm-start contract. Both use the existing component/runtime operation path and source, rights, permission, approval, placement and execution gates. This adapter does not bypass active project guards or replace their `required_guards` dependencies.

The v2 capability is initially single-process CPU, float32, eager registered train and validation splits, gradient accumulation 1, zero data-loader workers, and the installed Transformers 4.57.1 / Accelerate 1.11.0 implementation. No model, tokenizer or dataset download occurs. Users provide independently admitted assets and registered data. Sequence classification supports `eval_loss` or `eval_accuracy`; causal LM supports Trainer's `eval_loss`. These are explicit framework metrics, not a claim about universal convergence or a recommended stopping rule.

Parameters reuse the existing architecture, learning rate, AdamW, seed, batch size, weight decay, warmup, scheduler and gradient clipping options. Select:

- `horizon_epochs`: the original complete Trainer/scheduler horizon. One `Trainer.train()` call runs against this horizon; stopping early does not shorten or reconstruct its scheduler.
- `policy`: a complete versioned generic policy. Built-in convergence rules select target or plateau, direction, measured metric, threshold, window, insufficient-window behavior and minimum/maximum epochs. Source-pinned custom continuation/predicate methods and combined policies use the existing Method registry and deterministic evaluator. Every rule is evaluated and reported; conflicting stop/continue decisions block instead of selecting one rule.
- `epoch_bounds`: explicit platform bounds for custom/combined policies, with maximum epochs, optimizer steps, runtime, projections and units. A single built-in convergence policy can use its already selected bounds for compatibility. If convergence rules occur in a combined policy, their bound fields must agree explicitly with these platform bounds.
- `evidence_bindings`: maps every non-convergence rule ID to explicit fact selectors. Custom scientific fields receive measured data selected by these bindings; shared continuation status/checkpoint/cursor/resource/capability facts cannot be overwritten.
- `max_lineage_records`: explicit storage capacity for the ordered training row receipts across the full horizon. It must cover registered train rows times horizon epochs.
- Resource step unit `optimizer_steps`, with `next_epoch_steps` equal to the actual number of batches per complete epoch. Cost is explicitly `not_applicable` with unit `local-free`, because this local adapter has no monetary accounting provider. Runtime can be `active` or `not_applicable`; active runtime measures cumulative wall seconds inside Trainer calls, carried across exact resumes. `next_epoch_seconds` is the user-selected admission projection. Epoch policy runtime projections are not a hard process timeout; the existing execution timeout remains independent.

Native project/run/recipe/step identity is captured by the platform before fresh-process stage isolation, forwarded in the inert execution spec and independently checked against native run ownership. `max_parallel_stages > 1` does not require a child ZenML ContextVar. Caller-selected `rule_subject` values are rejected; direct local function tests derive a clearly local component subject and cannot claim native run ownership.

All active budget dimensions are checked before epoch zero; equality is exhausted even with a zero projection. Built-in `convergence/v1` full-history evidence supports at most 10,000 selected epochs, so an unsupported maximum is rejected at admission. Custom methods retain their explicitly selected full history; no method history is silently truncated.

At each completed epoch, Trainer evaluates the registered held-out split and saves its native model, optimizer, scheduler, RNG and trainer state. The adapter verifies a whole-epoch row cursor, evaluates the deterministic selected policy, and atomically publishes a manifest-bound checkpoint containing original options, actual observations and reasons. It checks the decision before Trainer can enter another epoch. A criterion stop and a resource-bound stop remain distinguishable. The saved `decision` preserves the full shared-engine scientific result; separate `admission` records platform resource bounds and consumption. A custom method’s scientific `continue` is not rewritten as convergence when a platform bound requires stopping. Missing metrics, invalid evidence and blocked decisions fail; they do not trigger inference or an automatic retry.

`exact_state` continuation requires every native state file, verified asset hashes, the same registered row bytes/order identities, full options and original scheduler horizon, matching component/environment/source identities, and a completed epoch whose stored policy decision and independent budget admission both permit continuation. Resume regenerates every rule’s bound evidence from native epoch/step counters, measured native Trainer history, verified state assets, stored runtime and sampler cursor. It requires canonical equality with the saved evidence/decision/admission before calling Trainer. Stored scientific history and runtime cannot be restored independently of the evidence that authorized them. A seedable random sampler uses the selected seed plus Trainer's completed-epoch cursor; no partial batch is guessed or skipped. The native trainer state determines the original optimizer step/horizon. Checkpoints include actual ordered row receipts. Resume reproduces the pinned seedable sampler for each complete epoch and compares exact order and content, rejecting a resealed arbitrary permutation as well as missing/duplicated rows. Earlier observations retain their original series subject unchanged; continuation manifests separately identify the current native run and exact parent manifest digest. No historical metric is reassigned to a new run.

Explicit `warm_start` loads only verified model weights and starts a new optimizer/scheduler/RNG/data-order series under the current options. It does not restore an exact epoch cursor. Existing v1 evaluation and export adapters accept v2's hash-verified model/config/tokenizer assets; no other adapter family is accepted implicitly.

Cancellation before training starts performs no epoch. Cancellation during a partial epoch leaves only previously committed complete-epoch checkpoints eligible for exact continuation. Cancellation at a committed boundary preserves that boundary. A terminal stopped/blocked decision is not an exact continuation license. An existing Trainer/checkpoint output directory rejects retries before replaying optimization; common operation idempotency and dispatch enforcement remain independent.

The regression fixture uses an independently authored tiny local BERT model with nonzero hidden and attention dropout. Fresh-process uninterrupted/resumed comparisons check model tensors, optimizer and scheduler values, Python/NumPy/Torch RNG state, selected metrics, native Trainer epoch/horizon and exact row order. Additional tests cover actual plateau collection/stopping, an uneven final minibatch, a tiny local causal LM, custom noisy-flat/patience methods, positive and conflicting combined policies, serial/isolated native stages, caller-subject rejection, partial cancellation, resealed partial state, missing/tampered assets, changed options/horizon/seed/policy, cursor conflicts, safe stopping and warm-start differences. Native acceptance reuses the existing reviewed portable-dataset DAG, evaluator, live checkpoint observer and fresh-process export path.

The component-only parity tests do not establish whole-DAG continuation. The additional shared-service regression now establishes exact continuation for one static five-node CPU/eager DAG: registered train/validation imports, one Trainer v2, evaluation and export. Broader DAGs and carried iteration state remain unclaimed. Streaming datasets, distributed/GPU/MPS exact continuation, metrics outside the measured Trainer loss/accuracy fields and MLX exact continuation remain unsupported by this version. Registered custom methods may implement their own scientific algorithms using explicitly bound facts; no inline expression evaluator is provided.

## Explicit measured evidence bindings

For a registered continuation method that expects `facts["values"]`, select:

```json
{"flat":{"values":{"source":"metric_history","metric":"eval_loss"}},
 "identity":{"actual":{"source":"identities"}}}
```

The corresponding policy includes the complete source-pinned `method/v1` declaration for rule `flat` and an `identity/v1` rule, for example expecting `status: completed`. A noisy-flat method's window, width, patience and minimum epochs are versioned method parameters, never adapter hardcodes. The exact declaration must belong to the admitted recipe source commit/file closure; native dispatch loads it through the existing registry/source loader.

Selectors copy native `status`, counters, checkpoint identity/state, capability, units, row lineage, identities, current `epoch_metrics`, full `metric_history` or typed `observations`. Metric selectors name `eval_loss` or classification `eval_accuracy`; unknown/unavailable metrics or sources fail admission. Continuation safety facts are platform supplied and cannot be overridden by a binding. An `overlap/v1` predicate requires independent cross-run/cross-lineage comparison receipts which this single-run epoch adapter cannot obtain; admission reports that missing capability instead of mislabeling train/validation splits as cross-run evidence. `representation/v1` needs registered before/after stratum-count receipts which this epoch adapter cannot obtain; admission reports that capability limitation rather than fabricating counts.

The independent platform budget and every applicable continuation rule's facts share the same authoritative completed epoch, optimizer step, runtime, checkpoint state and data cursor. Scientific fields selected by the method remain independent. Resume preserves the original series subject and records the current native execution separately; historical observations are not assigned to a different run.

Reviewed custom-method imports and policy evaluation preserve Python, NumPy legacy and Torch CPU RNG state when those libraries are already loaded. Evaluation and resume-decision verification restore these states even on exceptions. Thus a deterministic-output method may consume/reset these RNGs without changing subsequent model dropout or the native saved RNG trajectory. The helper does not import optional ML libraries or initialize CUDA; imports before training initialization are followed by the adapter's explicit selected seed. This is RNG state preservation, not a general Python I/O, process, library-configuration or global-object sandbox; the reviewed deterministic-source contract remains required.

Epoch admission uses the shared evaluator's exact decimal-rational numeric conversion for both current consumption and next-epoch projection. For example, consumed runtime `0.1` plus projection `0.2` fits a selected bound `0.3`; current consumption already equal to the active bound still stops even when the projection is zero. No epsilon or hidden tolerance is introduced.

## Shared-service continuation acceptance

`tests/components/test_transformers_service_resume.py` exercises actual `run.submit`, `run.cancel`, native recovered-checkpoint discovery via `model.checkpoint.get`, and `run.resume(mode=exact_state)` through OperationService/ZenMLBackend. It uses independently authored dropout model/tokenizer/rows, explicit per-source dataset/model/source reviews and immutable registered references. The source-owned fixture synchronization waits at a completed epoch boundary; cancellation uses the real service operation. No training/scientific parameters are changed to create a partial run.

Uninterrupted and resumed controls reach the original full scheduler horizon with identical model tensors, optimizer, scheduler, Python/NumPy/Torch RNG, exact row order and selected held-out metrics. Native evaluator/export steps run, fresh-process export verification passes, and common export inspect/package operations bind each native selected checkpoint. The test edits the current recipe but verifies exact continuation keeps the parent contract and immutable parent request; warm start is not substituted. Read-only/untrusted resume requests fail. Test-owned native archives are temporarily corrupted and restored to exercise partial native Trainer state, changed stored horizon and missing optimizer rejection through the real resume path. Failed/cancelled workers and supervisors must be stopped, and no resumed complete-epoch checkpoint may be produced for unsafe inputs.

This is static-DAG CPU/eager acceptance, not a claim about distributed, streaming, MLX, conditional or bounded-iteration whole-DAG continuation. No runtime implementation change was necessary for the supported service path.

The service fixture instruments actual `Trainer.train` and `AdamW.step` entry, verifies those markers in positive runs, and requires their absence for each unsafe checkpoint. Negative assertions require the exact checkpoint-validation `ValueError` message for partial/changed state or missing assets; unrelated backend availability failures cannot satisfy them. Each export must bind its own run's selected checkpoint digest. A test-wide teardown examines every created operation, cancels any remaining owned work, waits for termination, and verifies worker/supervisor identities and worker process-group absence. Timeout cancellation uses the same termination verification; it does not extend the training or step deadlines. Native archive restoration remains protected by `finally`.
